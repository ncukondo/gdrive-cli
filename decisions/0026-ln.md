# 0026: `gdrive ln <target> <folder>` creates a shortcut

Date: 2026-08-03
Status: accepted

Extends [0025](0025-shortcuts.md).

## Context

[0025](0025-shortcuts.md) teaches the CLI to *read* shortcuts and deliberately
leaves creating them out, on the grounds that it is a new command with its own
naming questions and should be designed once reading is settled. This record
answers them.

Creating one is a single `files.create`: the shortcut MIME, a parent, and
`shortcutDetails.targetId`. The design surface is not the call, it is the
command's shape — what it is called, which argument comes first, what the
shortcut is named when the user does not say, and what happens when the target
is itself a shortcut.

## Decision

### 1. `ln`, alongside `cp` and `mv`

```
gdrive ln <target> <folder> [--name <name>]
```

The Drive file commands are already the POSIX set — `ls`, `mkdir`, `mv`, `cp`,
`rm` — so `ln` is the name a user guesses, and the argument order is `cp`'s and
`mv`'s: the thing, then where it goes. A noun group (`gdrive shortcut create`)
would put the one operation that belongs with `cp` in a different part of the
help output, and `cp --shortcut` would make a single command mean two unrelated
things depending on a flag.

`ln` creates a Drive shortcut, which is the only kind of link Drive has. There
is no hard-link sense to disambiguate, so the command takes no `-s`.

### 2. Both arguments follow, per 0025's role table

`<target>` is a **content** argument and `<folder>` a **container** one, so both
resolve through `resolveTarget`. These are the rows 0025 §1's table gains.

For `<folder>` this is `mv`'s and `cp`'s destination rule unchanged. For
`<target>` it means `gdrive ln Inbox/link-to-doc Archive` creates a second
shortcut to the *document*, not a shortcut to a shortcut — which Drive refuses
to store anyway. Following turns a request the API would reject into the one the
user meant, and it agrees with 0025 §5: a chain is a state that should not
exist, so no command should be able to produce one.

### 3. The default name is the target's name

Omitting `--name` names the shortcut after its target, which is what the Drive
UI does. Drive's own default is `Untitled`, so leaving the field unset is not an
option worth having.

`ln` therefore needs the target's metadata. `resolveTarget` already returns it
when the argument was a bare id ([0025](0025-shortcuts.md) §4), so the cost is
one `files.get` and only when `<target>` was written as a path *and* `--name`
was omitted.

### 4. Drive decides what links are legal, and says so itself

Shortcuts have placement rules — a shared drive will not hold a shortcut to a
file outside it, and the rules differ by the drive's sharing settings. `ln` does
not pre-check any of them. It issues the create and lets the failure travel
through `mapDriveError` like every other Drive refusal.

A pre-flight check would duplicate a policy that is Google's to change, and
would have to fetch both drives' configuration to do it — paying two round trips
on every successful `ln` to phrase an error the API already phrases correctly.

### 5. Output is the created file, like `mkdir` and `cp`

JSON `data` carries `file`, the new shortcut as a full file object, so
`target_id` and `target_type` are in the response ([0025](0025-shortcuts.md)
§2). Text names both ends, because the shortcut's id alone does not tell the
user the link landed on the right file:

```console
$ gdrive ln "Reports/2026 Budget" "Shared/Links"
Created shortcut 2026 Budget (1Lnk…) -> 2026 Budget (1AbC…)
```

Quiet prints the new shortcut's id, matching `mkdir` and `cp`.

### 6. `files.create` gains a shortcut body

`FileCreateBody` gains `shortcutDetails: { targetId }`, checked against
`drive_v3.Schema$File` by `GeneratedParamChecks` like every other field
([0015](0015-no-type-assertions.md)). The call sets `supportsAllDrives: true`
and requests `FILE_FIELDS`, as `copyFile` does.

## Out of scope (deferred)

- **Retargeting an existing shortcut** (`files.update` on `shortcutDetails`).
  Deleting and re-creating is one extra command and does not need a design.
- **`--force` / overwrite semantics.** Drive allows duplicate names in a folder,
  `mkdir` and `cp` do not check for them, and `ln` has no reason to be the
  command that starts.
- **`resourceKey`** for link-shared targets. It belongs to addressing generally,
  not to `ln`, and no command handles it today.

## Consequences

- `ln` can create a shortcut whose name collides with a sibling. Nothing new
  breaks: a path segment matching two files already errors `INVALID_ARGS`
  listing the candidate ids ([0008](0008-drive-commands.md)), and that is the
  message the user gets.
- Naming the shortcut after its target means `ln x Folder` twice into the same
  folder produces exactly that collision. It is the same trade the Drive UI
  makes, and `--name` is the escape.
- `gdrive ln` is the first command whose `<target>` argument is content-role
  while its output is a new *entry*. 0025's table stays the single place that
  says which arguments follow; this record adds two rows to it rather than
  introducing a second rule.
